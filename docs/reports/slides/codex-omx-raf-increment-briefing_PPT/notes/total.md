# 01_conclusion

这一页先给结论，不进入代码细节。这轮工作的重点不是又加了一批 prompt 或 skill，而是让 OMX 开始从“会执行”转向“可治理地完成复杂目标”。原来的 OMX 已经有很强的运行时和多 agent 调度能力，但复杂任务里真正容易出问题的是目标没有先冻结，执行过程很快偏向一个看似完成但不满足真实意图的产物。

本轮增量可以压缩成三点：第一，RAF 把目标契约、架构规格和实现闭环串起来；第二，动态 agent/skill 让专家能力可以在项目层试验和刷新；第三，PPT 路径作为首个验证场景，能用真实 editable PPTX 来检验这套机制是否真的落地。

# 02_why_care

这一页从上级视角讲为什么需要关心。复杂任务失败往往不是模型完全做不出来，而是太早进入执行。目标没有冻结时，AI 会根据局部上下文优化；缺少多视角反推时，产物可能只满足实现者视角；失败只做局部修补时，问题没有回到目标或规格层。

对管理侧来说，这对应三个成本：返工成本、不可复用成本和难评估成本。RAF 的价值不是增加流程负担，而是把这些风险前置成可审阅控制点：目标契约先说清楚什么算成功，架构规格再定义什么路径最可能成功，实施阶段用证据验证并做失败归因。

# 03_omx_vs_raf

这一页要注意不要把 OMX 和 RAF 讲成竞争关系。原 OMX 是强执行底座，擅长 skill、agent、runtime、team、hook、HUD 等编排能力。RAF 是叠加在这个底座上的任务治理层，用来规定复杂目标进入执行前必须具备哪些目标和规格资产。

所以本轮增量不是替换原 OMX，而是让原来的执行能力有了更强的入口约束和验收回路。原来用户更像是在选择某个工具或模式；现在可以先形成 goal contract 和 architecture/spec，再由执行阶段消费这些资产。这是从“工具复用”到“任务组织方法复用”的变化。

# 04_raf_v_model

这一页是方法论核心。RAF 三层 V 架构可以理解为：左侧先把目标和规格逐层收紧，右侧执行和验证时再把失败反向归因回来。Stage 1 是 goal-setting，负责目标、受众、非目标、验收标准和授权边界。Stage 2 是 architecture-spec，负责视角反推、方案变体、反证测试和实现规格。Stage 3 是 ralph-implement，按批准的规格执行，并收集证据。

关键点是 backprop。失败不再默认是实现层问题，而要判断是目标错、规格错，还是实现错。如果目标和受众判断错了，就回 Stage 1；如果方案或视角缺失，就回 Stage 2；如果只是生成或代码错误，才留在 Stage 3 修复。

# 05_dynamic_loading

这一页讲工程增量。过去新增专家角色更像是修改源码、打包、安装，再使用。现在项目可以通过 `.codex/prompts/*.md` 和 `.codex/agents/*.toml` 定义专家，再通过 `omx agents refresh` 同步到 native agent TOML。这让专家能力可以先以项目级形式试验，验证有效后再考虑是否沉淀为通用能力。

这里要明确边界：这不是任意 JS/TS 代码插件动态执行，而是角色、元数据、模型策略和指令的动态加载。这个边界更安全，也更适合当前阶段。它解决的是专家能力扩展和验证成本问题，而不是把所有代码执行都插件化。

# 06_ppt_validation

PPT 路径是第一个验证场景，但不是 RAF 的边界。它适合作为验证场景，是因为 PPT 同时要求目标清楚、受众明确、叙事成立、视觉可读、讲稿可用，并且最后必须导出 editable PPTX。一个只会写提纲的流程无法通过这个场景。

这次我们还把 `ppt-master` 的依赖关系理顺了：GitHub 版 OMX 不直接内嵌大体量的 ppt-master 仓库，而是通过 `ensure-ppt-master-skill.sh` 自动检查本地配置或拉取 Bitbucket 依赖。这样本地使用方便，公开仓库也保持轻量。如果拉取失败，系统必须明确报出依赖 URL，而不是用别的工具伪造产物。

# 07_evidence

这一页只用于支撑判断，不做代码走读。RAF 已经不是口头概念，因为 `goal-setting`、`architecture-spec`、`ralph-implement` 都有对应 skill contract。PPT 也不是单独孤岛，因为 `raf-ppt` 已经变成兼容入口，真正路径是通用 RAF 三阶段里的 PPT route。

动态加载由 `src/agents/registry.ts` 支撑，刷新入口由 `src/cli/agents.ts` 和 `.codex/agents/*.toml` 支撑，契约由 `registry.test.ts` 和 `raf-ppt-skill-contract.test.ts` 保护。插件侧还有 `plugins/oh-my-codex/skills/*` 和 catalog manifest。这里的目的就是让上级知道这些结论都有实现依据。

# 08_risks

这一页主动讲边界和风险，避免过度承诺。第一，动态加载不是任意代码插件，JS/TS 代码插件需要另一个安全模型。第二，RAF 不是 PPT 工具，PPT 只是第一条验证路径，后续还要沉淀代码、报告、研究等 artifact route。第三，新专家质量需要治理，项目级试验通过后才适合提升为内置。第四，当前还不能停在文档层，需要用真实 PPTX 完成端到端闭环。

这页的作用是提高可信度。我们不是说所有问题都已经解决，而是说明当前边界在哪里，下一步怎么把能力继续收敛成稳定机制。

# 09_decision

最后一页回到希望上级做出的判断。建议确认 RAF 作为下一阶段复杂任务组织模型，把动态 agent/skill 作为专家能力试验机制，并把 PPT 作为第一条端到端验证路径。

短期动作是完成本 PPT 的 ppt-master 产物闭环，真正生成 design spec、spec lock、SVG 页面和 editable PPTX。中期是补齐更多 artifact routes，让代码、报告、研究等产物也能复用同一套目标-规格-执行闭环。长期则是建立动态专家能力的治理标准，明确什么时候项目级 agent 可以沉淀为通用能力。
